# 프로젝트 기획명세서

**팀명**: 세이프메이트 (SAFE MATE)
**서비스명**: 도와줘, 맵!
**부제**: 실시간 위험구간 제보 & 가중치 기반 안심 귀갓길 추천 서비스

---

## 1. 프로젝트 개요

### 1.1 기획 배경
늦은 밤 귀갓길이 불안하지만 정확히 어디가 위험한지 정보가 없다는 문제를, 시민 제보 데이터로 해결하고자 기획함.

### 1.2 문제의식
- 기존 지도 서비스는 '단순 최단거리' 경로만 제공하며, 보행자의 체감 안전도를 반영하지 않음
- 가로등 고장, 인도 파손, 어두운 골목 등 위험 요소는 발생 시점마다 달라지지만, 이를 실시간으로 반영하는 서비스는 없음

### 1.3 프로젝트 목표
공공데이터(보안등·CCTV 등)와 시민 실시간 제보를 결합해, 기존 '단순 최단거리' 방식에서 벗어나 안전 지표를 반영한 '가장 안전한 보행 경로'를 실시간으로 추천하는 서비스를 만든다.

### 1.4 진출 목표 산업
스마트시티·도시안전 솔루션 — 공공데이터와 시민 참여 데이터를 결합해 지자체·공공기관에 공급 가능한 안전 인프라 서비스로 확장을 목표로 함.

### 1.5 플랫폼
반응형 웹 (Mobile Web / PC 대화면 뷰포트 지원)

## 2. 서비스 대상 및 범위

### 2.1 타겟 사용자
- 늦은 밤 도보로 귀가하는 시민 (자취생, 야간 근무자 등)

### 2.2 서비스 지역 범위
- **1차 구현(MVP) 범위**: 시연이 가능한 동네 1~2곳으로 한정 (카카오맵 검색 및 지도 표시가 가능한 범위 내)
  - 데이터 정리와 알고리즘 테스트를 빠르게 진행하기 위한 전략
- **확장 계획**: 서울 전역 → 인구 밀집 지역(경기도 등) 순으로 확대 검토 중 *(팀 논의 후 확정 예정)*

> 참고: 서울은 "안심귀갓길" 관련 공공데이터가 경로 단위로 정리되어 있어 1차 구현에 유리하나, 경기도는 시·군별로 데이터가 분산되어 있어 별도 통합 작업이 필요함. 지역 확장 범위는 팀 내 추가 논의 후 확정.

## 3. 핵심 기능 명세

| 기능 | 설명 |
|---|---|
| 실시간 위험구간 제보 | 가로등 고장, 어두움, 인적 드묾 등 카테고리별 제보를 지도 위에서 등록 |
| 가중치 기반 안심 경로 추천 | 최단 경로와 안심 경로를 동시에 계산·비교 제시 |
| 제보 알림/히트맵 | 실시간으로 들어오는 제보를 지도 위에 마커·히트맵으로 표시 |
| 마이페이지 | 내가 등록한 제보 목록 + 자주 가는 경로 즐겨찾기 (즐겨찾기는 독립 화면이 아닌 마이페이지 하위 기능) |

### 기능 우선순위 (MVP vs 고도화) *(9월 팀 회의로 확정)*

**MVP (1차 구현, 필수)**
- 홈/지도 화면 — 지도 표시, 출발지·도착지 검색, 최단/안심 경로 듀얼 표시
- 제보 등록 — 지도 클릭 시 카테고리 선택 + 사진 첨부로 위험구간 제보
- 제보 알림/히트맵 — 실시간으로 들어오는 제보를 지도 위에 마커·히트맵으로 표시
- 마이페이지 — 내 제보 목록, 즐겨찾기 (별도 탭이 아닌 마이페이지 통합 기능)

**고도화 (여유 시간에 따라 추가)**
- 서비스 소개/이용안내 — 처음 온 사용자에게 서비스 설명 (다른 필수 기능 다 끝난 뒤 시간 남으면 진행)
- 제보 카테고리별 차등 가중치 (가로등 고장 등 객관적 위험 vs 인적 드묾 등 주관적 체감을 구분 반영)
- 시간 감쇄 로직 정교화 (오래된 제보 영향력 감소)
- OSM(OpenStreetMap) 기반 도로망 자동 확장 — 보행로 그래프 구축 자동화로 시연 구역 확장이 용이해짐
- 제보 신뢰도 검증 고도화 — 동일 사용자 중복 제보 필터링, 다중 제보 신뢰도 점수화 등 어뷰징 방지
- 제보 카테고리 확장 — 현재 3종 외 "인도 파손", "CCTV 사각지대" 등 기존 컨셉(지속적 환경 위험)과 맞는 카테고리부터 추가 검토
  - 지진 등 자연재해/사고 신고는 별도 검토 대상: 즉시 전체 알림이 필요한 성격이라 지금 제보 구조(경로 가중치 누적)로는 처리 불가하고, 이미 국가 긴급재난문자 체계가 지진을 다루고 있어 시민 제보로 다루는 실익도 불확실함

## 4. 시스템 아키텍처

### 4.1 전체 구조 (흐름)
```
[사용자 - React 웹] 
   ↕ REST API (제보 CRUD)
   ↕ WebSocket/STOMP (실시간 브로드캐스팅)
[Spring Boot 서버]
   ↕
[MySQL DB] ← 공공데이터 정제·적재 (보안등, CCTV 등)
```

### 4.2 기술 스택

| 영역 | 도구 |
|---|---|
| Frontend | React |
| Backend | Spring Boot |
| 지도 API | Kakao Maps SDK (JavaScript 키 · REST API 키 병행 사용) |
| 실시간 통신 | WebSocket (STOMP + SockJS) |
| DB | MySQL *(추후 여유 시 AWS 기반 DB로 확장 검토)* |
| 그래프/알고리즘 | Java (Spring 내부) 또는 Python |
| 개발 도구 | GitHub · VS Code · Figma |
| 배포/시연 | 로컬 서버 + 같은 Wi-Fi 네트워크 |

### 4.3 담당 기능 상세
- **Frontend**: Kakao Maps SDK 연동, 반응형 지도 UI, 최단/안심 경로 듀얼 렌더링, 실시간 알림 UI
- **Backend**: 제보 CRUD REST API 개발, WebSocket/STOMP 실시간 브로드캐스팅
- **Data/알고리즘**: MySQL 기반 DB 설계, 공공데이터 정제·공간 인덱싱, 커스텀 다익스트라 경로 알고리즘

### 4.4 Kakao API 키 및 보안 설정
- **JavaScript 키**: 프론트엔드(React)에서 지도 화면을 그리는 용도
- **REST API 키**: 백엔드(Spring Boot)에서 주소 검색·좌표 변환 용도
- API 키 등 민감한 값은 `application.yml`에 직접 적지 않고 `.env` 파일로 분리 관리
  - `application.yml`: 설정 틀만 작성해 Git에 공유 (예: `rest-api-key: ${KAKAO_REST_API_KEY}` 형태로 환경변수 참조)
  - `.env`: 실제 키 값 보관, Git에서 제외(`.gitignore`)
  - 프론트(React)와 백엔드(Spring Boot)는 `.env` 파일을 각자 프로젝트 루트에 별도로 둠

## 5. 데이터 설계

### 5.1 외부 연동 데이터 vs 자체 수집 데이터 구분

| 구분 | 역할 | 소스 |
|---|---|---|
| 배경 위험도 (정적) | 평소 해당 경로의 안전 인프라 수준 | 공공데이터 (보안등·CCTV 위치 등) — 보조 지표 |
| 실시간 위험도 (동적) | 지금 이 순간 발생한 위험 상황 | **자체 DB + 시민 제보 (직접 구현)** — 서비스의 핵심 차별점 |

> 정부의 시민 제보 데이터(예: 안전신문고)는 외부 개발자가 활용 가능한 공개 오픈API 형태로 확인되지 않아, 실시간 제보 기능은 자체 개발로 진행함.

### 5.2 데이터베이스 설계 (개요)
- 제보 테이블: 위치(좌표), 카테고리(가로등 고장/어두움/인적 드묾 등), 등록 시각, 신뢰도 점수 등
- 사용자 테이블
- 경로/그래프 테이블: 보행로 교차로 노드, 간선(거리·위험 가중치)
- ERD는 개발 착수 후 구체화 예정

## 6. 핵심 알고리즘 설계

### 6.1 경로 추천 알고리즘
- 가중치 그래프 기반 다익스트라 변형 알고리즘
- 거리뿐 아니라 위험도(제보 밀도·최신성)를 간선 가중치에 반영해 '안심 경로' 산출
- 최단 경로와 안심 경로를 동시에 계산해 비교 제시

### 6.2 실시간 반영 & 시간 감쇄
- 제보 등록 시 해당 좌표 주변 구간의 위험 가중치를 즉시 갱신
- 오래된 제보일수록 가중치 영향력이 감쇄하는 함수 적용 (감쇄 속도는 카테고리별로 차등 설계 예정)

### 6.3 제보 신뢰도 검증 (어뷰징 방지)
- 동일 사용자 중복 제보 필터링
- 다중 제보 신뢰도 점수화

## 7. 디자인 컨셉 & 화면 설계

### 7.1 색상 컨셉
"안심감"과 "경고감"을 동시에 표현하는 방향으로 **네이비 + 옐로우/앰버 + 레드** 조합을 채택.

| 용도 | 색상 | 비고 |
|---|---|---|
| 메인(배경/기본 톤) | 딥 네이비 (`#1A2B4C` 계열) | 밤길, 신뢰, 안정감 |
| 포인트 | 앰버·옐로우 (`#FFB020` 계열) | 가로등 불빛 느낌, 안심 경로 표시 |
| 위험구간 강조 | 레드 계열 | 위험 마커만 명확히 눈에 띄도록 대비 |
| 보조 | 화이트/라이트 그레이 | 가독성 확보용 배경 |

- 최단경로(회색/파랑 계열) vs 안심경로(옐로우/앰버)를 색으로 구분해 듀얼 렌더링 시 시각적 차별성 확보
- 위험구간 마커만 레드로 튀게 하고 나머지는 차분한 톤 유지 → "진짜 위험한 곳만 눈에 띄는" 구조로 사용성과 발표 임팩트 모두 고려

### 7.2 전체 화면 구성 *(9월 팀 회의에서 구조 단순화로 확정)*

핵심 기능이 사실상 "지도 하나"에 집중된 서비스라, 네비게이션을 복잡한 하단 탭 대신 아래처럼 단순화함.

**네비게이션 구성**

| 항목 | 용도 |
|---|---|
| 로고/서비스명 (도와줘, 맵!) | 클릭 시 홈(지도 화면)으로 이동 |
| 위험 제보하기 | 제보 등록 모달을 바로 여는 버튼, 눈에 잘 띄게 배치 |
| 마이페이지 | 내 제보 내역, 즐겨찾기 |
| 서비스 소개 (선택) | 처음 오는 사람을 위한 안내 |

**화면 목록 및 우선순위**

| 우선순위 | 화면 | 설명 |
|---|---|---|
| 필수 | 홈/지도 화면 | 지도 표시, 출발지·도착지 검색, 최단/안심 경로 듀얼 표시, 실시간 제보 마커·히트맵 오버레이 |
| 필수 | 제보 등록 | 지도 클릭 시 위험구간 제보 모달 (카테고리 선택, 사진 첨부) |
| 필수 | 마이페이지 | 내가 등록한 제보 목록, 자주 가는 경로 즐겨찾기 (즐겨찾기는 독립 화면이 아닌 마이페이지 하위 기능) |
| 선택(고도화) | 서비스 소개/이용안내 | 서비스가 뭘 하는지 처음 온 사람에게 설명 — 나머지 필수 기능 완성 후 시간 남으면 진행 |

> 이전 검토안이었던 "즐겨찾기·알림 독립 탭 + 로그인 화면" 4탭 구조는 팀 논의를 거쳐 위와 같이 단순화하기로 확정함. 지도 화면과 제보 등록 두 가지만 확실히 동작해도 시연 임팩트는 충분하다는 판단.
> "제보 알림/히트맵"은 네비게이션 표(위)에 진입 경로가 없어 독립 화면이 아니라 홈/지도 화면 위에 얹히는 오버레이 기능으로 정리함 (위 표에 반영).
> **확인 필요**: 새 구조에는 로그인/회원가입 화면이 명시되어 있지 않음. 제보자 식별·중복 제보 방지·마이페이지 접근을 위해 최소한의 사용자 구분이 필요한지, 필요하다면 어떤 방식(간편 로그인 등)으로 처리할지 팀 내 추가 논의 필요.

- 상세 와이어프레임은 Figma로 별도 제작 예정

| 1단계 | 기획 구체화 & 데이터/인프라 셋업 |

## 10. 기대효과 및 향후 계획

### 기대효과
- 보행자가 체감하는 실제 위험을 반영한 경로 추천으로 기존 지도 서비스와 차별화
- 시민 참여형 데이터 수집 구조로 정부 데이터가 놓치는 실시간 위험 정보 보완

### 향후 계획
- 시연 지역 확장 (OSM 기반 도로망 자동 확장 활용)
- 지자체·공공기관 대상 안전 인프라 서비스로 확장 검토
- 제보 신뢰도 검증 로직 고도화
